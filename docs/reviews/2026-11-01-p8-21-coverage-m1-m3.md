# ADR-0027 measurements M1–M3: script shells, PDF and image menus (P8-21, interim)

Session P8-21, 2026-11-01, after the owner's answers on ADR-0027 (all as recommended: M1, then
M2, then M3; `pypdf` only if M2 shows most menu PDFs have a text layer, and through a reviewed
dependency PR). Measurement only: no pipeline, schema, dependency or `infra/` change, and no
database written. Live fetches were polite (production User-Agent, robots obeyed, 3 s between
requests to a host). Scripts and outputs stay untracked in `var/p8-21/{m1b,m2,m2tools,m3}/`
(worktree `p8-21-validator-v11`); M1's draw is `var/p8-21/m1/draw.json` (worktree
`p8-21-dns-unresolved`).

**Status: M2 and M3 done; M1 interim (17 of 40 venues), still running when this was written.**

## Result

- **M1 (render more candidates): no gain so far.** 68 renders on 17 venues, **0 verified** at any
  rank. Ranks 3 and up are guessed well-known paths (`/food`, `/our-menu`) that 404 or render the
  same app shell as an earlier rank (24 of 68 renders repeat an earlier candidate's text).
  Raising `MAX_RENDER_CANDIDATES` is **not supported** by the interim data.
- **M2 (PDF menus): text layers are common, but the fetch policy blocks most PDFs first.** 37 of
  40 venues link a menu PDF; **18 links are refused** because the PDF redirects to another host
  (a site builder's file CDN), 3 exceed the 3 MB body cap, 1 robots. Of the 10 distinct menu PDFs
  downloaded, **9 have a text layer**, 1 is mostly images.
- **M3 (image menus): at most 318 of 2,432 `no_menu_found` venues (13 %)** show a menu-named image
  or image link, or an image-only menu page; about 4 in 10 of the image hits read are menus,
  so the real count is nearer 120–150 venues (5–6 %).

## M1. Script shells (interim)

**Draw** (frozen, seed 20261103): 30 of the 425 `no_menu_found` venues with three or more
JavaScript-only candidates in P8-20's discovery replay, and 10 of the 148 with one or two. The
draw keeps what the population holds, including non-restaurant websites (TikTok, Walmart, a
music site) and chains (Domino's three times, BJ's).

**Method.** A first attempt ran whole production discoveries with the render step widened. It took
about 17 minutes a venue (static discovery's fetches at 3 s each, then the renders), so it was
stopped after 2 venues. The run used here (`m1_direct.py`) renders only what M1 measures: each
venue's JavaScript-only candidates from the replay, in discovery's order, up to `MAX_MENU_PAGES`
(6). It uses the production `BrowserRenderer` (its robots and same-site rules) and the production
verifier (`classifier-v2+v3`) with discovery's trust rule: a well-known path on a catch-all site
is not trusted. Production renders the first `MAX_RENDER_CANDIDATES` (2) and keeps the first
menu.

**Interim (17 venues, 68 renders, 781 s of render time; median 9.5 s a render, max 39.7 s):**

What the renders show:

## M2. PDF menus

**Draw** (frozen, seed 20261104): 40 of the 164 `menu_pdf_only` venues.

**Method.** PDF links aren't stored (only the verdict), so each venue's link was found offline:
production's `menu_pdf_links` on the venue's cached homepage and candidate pages (P8-20's site
cache), first link in discovery's page order. Then one `SiteFetcher.fetch_page` of it: the
production robots, same-site redirect, public-address and 3 MB rules. (A first attempt re-ran
whole discoveries, about 6 minutes a venue, and was stopped after 4.) The bytes were scanned with
the standard library only (`m2_pdfscan.py`, run with `python -I`): Flate streams inflated, text
operators (`Tj`/`TJ` inside `BT`…`ET`) and image XObjects counted. No PDF library was added.

**Fetch outcomes (40 venues):**

| Outcome | Venues |
|---|---|
| Downloaded (`application/pdf`) | 15 |
| `skipped/redirect_refused` | **18** |
| `failed/too_large` (> 3 MB) | 3 |
| `skipped/robots_unavailable` | 1 |
| No menu PDF link in the cached pages | 3 |

- **The redirects.** 17 of the 18 are Squarespace-style `/s/<file>.pdf` links and 1 a Wix
  `/_files/ugd/` link; each redirects to the builder's file CDN on another host; SiteFetcher refuses any redirect that leaves the site.
  `menu_pdf_links` already counts PDFs on any host, but the fetch can't follow one this way.
- **The downloads** are 12 distinct files: one chain PDF serves 4 venues. 2 are nutrition PDFs
  (Olive Garden, Pizza Twist): the PDF-link rule takes "menu nutritional" files too.

**Text layer (the 10 distinct menu PDFs):**

| Verdict | PDFs | Detail |
|---|---|---|
| `text` (text operators showing ≥ 200 characters) | **9** | 1–27 pages; 950–20,000 characters shown |
| `little_text` (mostly page images) | 1 | 544 images, 77 characters (a scanned or image menu) |
| `image_only` / `unreadable` | 0 | |

The character counts come from the show operators' strings, so a font with a custom encoding can
count characters that a text library would not decode. Only a library run settles that.

**Against the owner's condition (Q2):** of the menu PDFs that can be fetched, **most (9 of 10) have
a text layer**, so the condition for adding `pypdf` holds. But the fetch policy decides more:
18 of 37 linked PDFs are never downloaded today. Owner questions below.

## M3. Image menus (offline count)

**Method** (`m3_images.py`, standard library): the 2,432 `no_menu_found` venues' cached homepage
and static candidate pages (P8-20's site cache: 2,431 homepages, 1,785 candidates). Per venue,
three signals:
- `menu_img`: an image whose alt, title or file name names a menu, excluding icons, logos and
  buttons, raster files only;
- `menu_img_link`: a link to an image file whose URL or text names a menu;
- `gallery`: a candidate page whose path names a menu, with under 400 characters of text and at
  least one image.

| Signal | Venues |
|---|---|
| Any image signal | **318** (13.1 %) |
| `menu_img` | 256 |
| `gallery` | 83 |
| `menu_img_link` | 25 |
| Any image signal and JavaScript-only candidates too | 16 |

**Read sample** (30 random `menu_img` hits): about 13 are menu images ("Fabrik Summer Menu 6
Course.png", "DRINK-MENU-1-pdf.jpg", "Main menu … Page_2.jpg", "Menú Pink Towers 2"). The
others are category tiles ("menu-tile-dessert.jpg"), article images ("Menu Hacks"), Instagram
posts, food photos and a banner. So 318 is an upper bound. With the gallery pages, about 120–150
venues (5–6 % of `no_menu_found`) likely have an image menu. The coverage set's image states are
still at 0. Reading them needs OCR or a vision model (Q3: measured only, for now).

## Owner questions

- **Q1. M1 decision.** If the remaining 23 venues confirm the interim result (no menu verified past
  rank 2), keep `MAX_RENDER_CANDIDATES` at 2 and close M1? *Recommended:* yes. The guessed
  well-known paths render the same shell, and each extra render costs about 10 s.
- **Q2. PDF fetch policy.** Let a PDF link follow a redirect to another host (a site builder's
  file CDN), as `menu_pdf_links` already accepts a PDF on any host? It is a change to the fetch
  policy, so it is the owner's call. *Recommended:* yes, for PDF links only, with the other rules
  kept (robots on the final host, public address, the cap). Without it, 15 of the 37 linked PDFs are
  fetched; with it, up to 33 of 37 (the 3 over the cap and 1 robots case aside).
- **Q3. The 3 MB cap for PDFs.** 3 of 40 exceed it. Keep the cap, or raise it for PDFs only (to
  10 MB)? *Recommended:* keep it for the first build and count `too_large`.
- **Q4. The `pypdf` dependency PR.** M2 meets the condition (9 of 10 fetchable menu PDFs have a
  text layer). Open the dependency PR (ADR + `pyproject` + lockfile, reviewed before any build)
  next? *Recommended:* yes, after Q2: the redirect rule decides the gain.
- **Q5. Nutrition PDFs.** 2 of the 12 downloaded files are nutrition tables. A PDF reader would
  meet Amendment 35's problem again; `validator-v11`'s numeric-table rule reads blocks, so it
  applies to PDF text only if the PDF reader emits one block per cell. Note it for the PDF ADR?
  *Recommended:* yes.
