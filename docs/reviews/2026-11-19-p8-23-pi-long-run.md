### Finding: a restored dump blocks Menu writes on another cluster (`menu.admission_fence`)

Batch 1's extraction stopped on its first page: `SerializationFailure: Menu admission snapshot is
stale`. `menu.lock_admission()` keeps the last admitting transaction id in the sequence
`menu.admission_fence` and refuses a writer whose snapshot can't see it. `pg_restore` carries the
sequence value over: `helios_work` held the laptop's 915,058 while the Pi's cluster was at
transaction 27,739, so every admission would have failed until the Pi's counter passed the
laptop's (about 890,000 transactions). Earlier Pi restores never hit it because the Pi never wrote
Menu pages. **Fixed for this run** (work database only): `setval('menu.admission_fence',
txid_current())` on `helios_work`, then the loop resumed; batch 1's pages stayed due and were
extracted in the next batch. Restoring a Pi dump into `helios_laptop` is safe (its fence value is
below the laptop's counter); the reverse, or any restore onto a younger cluster, needs the same
reset before Menu writes. Not changed in code (a migration-owned function): an owner question.

### Finding: most refetched pages change, and a changed text is extracted whole

Batch 1 (50 URLs, 92 records): 60 changed + 2 new Versions, 30 unchanged. Of 18 changed texts with an
older Version, the median change is 33 lines; real menu changes (new dishes, new prices) sit next
to churn: "ORDER NOW" → "Order Now", a byline's capitalisation, a footer link, CDT → CST, and on
delivery platforms ratings, preorder times and neighbourhood lists (Uber Eats' Chick-fil-A pages:
24–27 chunks each, changed throughout). Reusing saved answers per chunk instead of per page would
have skipped **30 of 146 chunks (0.21)**: chunks are cut by size, so an early insertion moves every
later chunk boundary. At 6 pages/h a batch of 50 URLs costs about 10 hours of extraction.
